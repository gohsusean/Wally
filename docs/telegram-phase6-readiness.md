## Minimum production rollout

The existing capability is suitable for a small, specifically authorized update
of **already populated Frequency or Amount Policy** on a registered record,
subject to a fresh source check and completed live presentation acceptance.
Production remains disabled; this assessment does not authorize a rollout.
In today's financial catalog, the only complete recurring definition is the
protected TNB record. The other 17 definitions need initialization before they
can qualify; none is currently a permitted production pilot under this task.

Essential requirements for the first eligible production edit:

1. Finish the new sandbox UI acceptance and refresh the connected MCP process.
2. Select one non-certified record with a complete, readable source snapshot.
   Financial targets require a designated source and matching canonical catalog
   object. Install an exact page/property/value allowlist and a separate Telegram
   target subset only after owner authorization. Keep the local write gate closed.
3. Show complete current/proposed values and any certification consequence. Read
   current source, policy and proposal again after the owner press and before
   dispatch. Independently verify approved values and all protected properties.
4. Obtain explicit acceptance of the remaining GET/PATCH concurrency limitation
   for that exact low-risk scope. Avoid simultaneous changes to that record during
   the interaction. This coordination reduces risk but cannot enforce exclusivity.
5. On interruption or uncertain outcome, inspect and independently verify; never
   repeat the PATCH or clear an unresolved claim automatically. A still-running
   attempt requires process-liveness reconciliation. Restore disabled writes after
   the supervised pilot.

The review found the existing safeguards intact: authenticated owner/private-chat
callbacks bound to delivered message, nonce, scope and expiry; separate runtime
decision and execution confirmations; fresh source/version/Matter/policy checks;
atomic proposal/page claims; minimal PATCH; independent GET verification;
certification invalidation; and durable replay/cursor recovery. Restricted channels
gain no execution, certification or payment capability from presentation changes.

External edits are detected when relevant reads run, not continuously. Observed
drift stales prior verification and affects mapped financial certification; it is
not automatically adopted, reverted or certified. Reverting values does not restore
trust. Notion has no demonstrated atomic conditional PATCH here: an external edit
between the final GET and PATCH can be overwritten without recoverable evidence.
Independent readback cannot eliminate that race. It blocks scopes requiring zero
lost-update risk; it is a scope-specific owner decision for low-risk metadata under
[ADR-047](decisions.md#adr-047-human-first-presentation-and-external-notion-reconciliation).

Continuous monitoring, richer network diagnostics and catching disconnects without
a LaunchAgent restart can wait for this narrowly supervised pilot. They do not
replace the required source checks or uncertainty handling. No new architecture,
hosting, Touch ID work or broad write permission is needed for an eligible edit.

  identifiers remain missing for management accounts at TM110, Arkadia and Sentral,

  Provider defaults do not automatically override record-specific billing evidence.

  certificate/refund administration. Decide whether management, sinking fund and
  water form one obligation or separate streams. Resolve responsibility separately
  from legal account holder, property ownership and administration.
- Arkadia, Sentral Suites and Casaman addresses and Tropicana unit aliases still
  need evidence-based review where they affect canonical identity. Sold/inactive
  rows remain in identity checks; status is not a uniqueness exemption.

The financial reader, select vocabularies, source designation, evidence-bound local
certification and independent verification already support these facts once valid.
They do **not** mean Telegram can write all those fields today.

Current scoped writes support only Frequency and Amount Policy selects, with valid
existing enum values. Blank current values are rejected. Financial edits also require
an existing canonical object; the incomplete rows do not yet have one. Therefore
simply registering the remaining pages or turning on a gate cannot safely initialize
them. Additional select fields, exact approved text values (namespace/charge key/type),
and incomplete-row initialization need a separately reviewed, narrow implementation
using the existing proposal/authorization/verification machinery. Identifiers,
addresses, relations, checkboxes and schema changes require their own property
contracts if later needed; there is no need to enable generic Notion editing.

Full reconciliation through Telegram cannot be completed with the current two-field
capability. Certification, invoice intake and chain enablement remain separate
local-owner operations and must not be added to Telegram as an incidental extension.
